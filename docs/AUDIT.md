# Аудит проекта EuroAutoDataHub

> Дата аудита: 2026-09-30. Состояние кода: ветка `main`, коммит `e10a244`.
> Связанные документы: [PRD](PRD.md) · [Роадмап](ROADMAP.md)

## 1. Краткий вывод

Каркас пайплайна собран правильно (Scrapy → Kafka → консьюмеры → PostgreSQL → FastAPI),
но **в текущем виде система не готова к ежедневной работе**:

1. **API не запускается**: неверный импорт middleware.
2. **Миграции в Docker не применяются**: URL БД и учётные данные захардкожены в `alembic.ini`.
3. **Статус «продано» систематически искажается**. Ошибка воспроизведена на реальной БД:
   обход марки `rover` помечает проданными **все** объявления `land-rover`, а обход `zuk` — все `suzuki`.
   Любая неполная выгрузка марки (403, сбой страницы) тоже массово «продаёт» живые объявления,
   а обратно объявления не «оживают» никогда.
4. **Пауза при блокировке (403) не работает**. После первой «паузы» обход тихо обрывается,
   и оставшиеся марки не собираются.
5. **На чистой БД паук не стартует**: список марок читается из таблицы объявлений, которая пуста.
6. Больше половины тестов (19 из 36) не выполняются из‑за ошибки отступов.
   Парсинг объявлений тестами не покрыт.

Поэтому первый этап роадмапа — **стабилизация и корректность данных**, а не масштабирование.
План из `docs/scaling_recommendations.md` (3 брокера Kafka, Redis, 32 параллельных запроса)
преждевременен: он ускорит сбор, но не исправит искажение данных и повысит риск блокировок.

## 2. Как проверялось

- Прочитан весь код сервисов, конфигурации Docker/Scrapy/Alembic, тесты и документы.
- Тесты запущены: `pytest` собирает **17** тестов из **36** объявленных.
- Импорт API: `ModuleNotFoundError: No module named 'fastapi.middleware.base'`.
- Миграции Alembic прогнаны на локальном PostgreSQL 16.
  С URL из `alembic.ini` они падают, с правильным URL создают колонки `timestamp without time zone`.
- `db_writer.process_ad_data` и `db_updater.update_sold_ads` прогнаны на реальной БД.
  Сценарий «rover / land-rover» воспроизведён.
- Живой обход otomoto.pl не выполнялся: в среде аудита сайт недоступен.
  Выводы о поведении сайта (лимиты пагинации, persisted query) помечены как **риски для проверки**.

## 4. Что сделано хорошо

- Разделение на сервисы и асинхронная доставка через Kafka.
- Использование GraphQL API вместо парсинга HTML: стабильнее и дешевле.
- Ключ сообщения Kafka = ID объявления (порядок обновлений по объявлению сохраняется).
- Pydantic‑схема на входе консьюмера, Alembic‑миграции, healthcheck у PostgreSQL.
- Есть заготовки для истории цен (`auto_ad_history`) и статистики API.

## 5. Рекомендации по архитектуре (кратко)

Подробно — в [PRD, раздел 8](PRD.md#8-целевая-архитектура).

1. **Сначала корректность, потом масштаб.** Данные с ложными продажами хуже, чем отсутствие данных.
2. **Явный учёт полноты обхода.** Нужны таблицы `crawl_run` и `crawl_shard`, где записано, сколько
   ожидалось, сколько собрано и был ли обход полным. Объявление снимается с публикации только после
   **N подряд полных** обходов его сегмента, в которых его не было.
3. **Хранить наблюдения, а не только текущее состояние.** Нужны `first_seen_at`/`last_seen_at` и журнал изменений
   (цена, пробег, статус). На этом строится вся аналитика и детекция аномалий.
4. **Kafka оставить, но упростить:** один брокер в режиме KRaft (без ZooKeeper), батчевая запись с
   `INSERT ... ON CONFLICT`, коммит offset'ов после коммита в БД, DLQ.
5. **Паук не должен зависеть от БД.** Список сегментов берётся из справочника в коде или из API сайта.
6. **Отказаться от кластеров, Redis и 32 потоков** до появления реальной потребности.
